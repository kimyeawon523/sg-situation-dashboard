# SG 상황관리 대시보드 — 공공시설 상황 대응 데이터 구조·지표 설계

> 공공시설 37곳에서 발생하는 상황을 **접수 → 판단 → 호출·전파 → 현장 확인 → 조치 → 종결·기록**의 흐름으로 표준화하고,
> 관제사 1명이 우선순위를 판단할 수 있도록 **상황 데이터 구조와 운영 지표를 설계해 6면 대시보드로 구현**한 프로젝트

## 2. 문제 정의

공단은 수영장·도서관·체육시설·주차장 등 성격이 다른 공공시설 37곳(서해구 25 · 검단구 12)을 운영합니다.
현행 업무 분석에서 확인한 문제는 다음과 같습니다.

| 문제 | 영향 |
|---|---|
| 시설마다 상황 유형과 대응 방식이 다름 | 같은 사고도 기록 항목·보고 경로가 달라 비교·집계 불가 |
| 접수·전파·조치 기록 기준이 없음 | "누가, 언제, 어디까지 처리했는가"를 사후에 재구성하기 어려움 |
| 위험도 기준 없이 접수 순서대로 처리 | 동시 다발 상황에서 우선순위 판단이 관제사 개인 경험에 의존 |
| 미조치·미응답 상황이 드러나지 않음 | 호출 후 응답이 없거나 보고가 늦은 건을 놓칠 위험 |

**핵심 질문:** 관제사가 화면을 보고 *"지금 무엇이, 어디서, 얼마나 위험하고, 누가, 어디까지 처리했는가"*에 즉시 답하려면 어떤 데이터를 어떤 구조로 쌓아야 하는가?

<br>

## 3. 접근 방법

```
① 업무 흐름 표준화    접수 → 사업장 통보 → 현장 확인 → 조치 완료 → 보고 완료(종결)
        ↓
② 분류·등급 체계      분류 4종(안전사고·보안·시설장애·기상·재난) × 유형 36종
                      등급 4단계(재난·긴급·주의·알림) — 위험도·확산 가능성·대응 시급성 기준
        ↓
③ 데이터 구조 설계    상황 1건 = 접수 정보 + 처리 단계 + 호출/응답 이력 + 체크리스트 + 상황일지 + 보고서
        ↓
④ 지표 정의          "누가 · 언제 보고 · 어떤 행동을 하는가"를 통과한 지표만 화면에 배치
        ↓
⑤ 대시보드 구현       6면 화면 + 화면 간 선택 연동 + 외부 공공데이터 연계
```

## 4. 데이터 설계

### 4-1. 상황 레코드 구조

모든 화면은 하나의 상황 레코드를 서로 다른 관점에서 읽습니다.
처리 시간 지표는 별도 입력 없이 **상황일지(log)의 타임스탬프에서 계산**되도록 설계했습니다.

| 필드 | 내용 | 활용 |
|---|---|---|
| `site` · `loc` · `type` · `category` · `grade` | 사업장 · 위치 · 유형 · 분류 · 등급 | 필터, 우선순위 정렬 |
| `entry` · `start` | 접수 경로(CCTV / 신고 / 센서·경보) · 접수 시각 | 경과 시간, 접수 경로별 비교 |
| `stage` | 처리 단계 5단계 | 미조치 / 보고 미작성 / 종결 판정 |
| `notices[]` | 호출·신고·보고 대상, 시각, 응답 시각 | 초동 시간, 미응답 판정, 차순위 호출 |
| `checks{}` | 체크리스트 항목별 완료 시각 | 절차 이행 확인 |
| `log[]` | 모든 행위의 시각·내용·작성자 | 단계별 체류 시간, 처리 이력 추적 |
| `repeat` | 같은 사업장·같은 유형 총 발생 횟수 | 반복 발생 사업장 식별 |
| `report{}` | 세부 위치 · 피해 · 조치 결과 · 원인 | 종결 필수 항목 검증 |

### 4-2. 상태 판정 규칙

사업장 상태는 아래 우선순위로 **하나만** 부여해, 한 사업장이 여러 화면에서 다른 상태로 보이지 않게 했습니다.

```
확인 불가 (AI·경보 연계 사업장 연결 끊김)
  > 미조치   (조치 완료 전 상황 존재)
  > 확인 필요 (미연계 사업장 정기 보고 2시간 초과)
  > 이상     (설비 경보 · 보조설비 이상 · 이상 보고)
  > 정상
```

### 4-3. 시나리오 데이터 관리

코드에 하드코딩된 예시 데이터를 모두 걷어 내고, **비개발 담당자가 엑셀로 시연 데이터를 관리**할 수 있도록 구조화했습니다.

| 시트 | 역할 | 검증 |
|---|---|---|
| 상황유형 | 유형명 · 분류 · 기본 등급 (36종) | 분류·등급 허용값 |
| 체크리스트 | 유형별 관제사 조치 항목 (226항목, 매뉴얼 근거 포함) | 유형명 참조 무결성 |
| 금일 상황 | 서버 시작 시각 기준 "N분 전" 접수 + 처리 단계 | 사업장·유형·단계 허용값, 보고 완료 시 필수 항목 |
| 전일 기록 | 종결된 전일 상황 (금일 지표와 분리) | 조치·종결 시각, 보고서 필수 항목 |
| 사업장 상태 | 보고 지연 · 이상 보고 · 연결 끊김 | 연계/미연계 사업장별 허용 이벤트 |
| 인력 부재 | 역할별 요일·사유 | 역할·사유 허용값 |

- 드롭다운 기반 입력 + 로더의 행 단위 검증 → 잘못된 행은 건너뛰고 **행 번호와 사유를 로그로 출력**
- 시각을 "분 전" 상대값으로 저장해, 언제 실행해도 같은 경과 시간으로 시연이 재현되도록 설계

## 5. 지표 정의

화면에 넣을 지표는 **누가 · 언제 보는가 / 보고 어떤 행동을 하는가 / 없으면 무엇을 놓치는가**를 통과한 것만 남겼습니다.

| 지표 | 산출 기준 | 보는 사람 · 시점 | 행동 |
|---|---|---|---|
| 미조치 건수 | 처리 단계가 '조치 완료' 이전인 상황 수 | 관제사 · 상시 | 0건이 아니면 목록 상단부터 처리 |
| 긴급 이상 미조치 | 재난·긴급 등급 미조치 + 미응답 호출 보유 건 | 관제사 · 즉시 | 카드 점멸 · 경고음 → 즉시 처리 |
| 미응답 호출 | 호출 후 등급별 기준 시간(재난·긴급 1분, 주의 3분, 알림 10분) 내 응답 없음 | 관제사 · 즉시 | 차순위 호출 (재난·긴급은 자동) |
| 점검 필요 사업장 | 정기 보고 지연 + 시스템 연결 끊김 사업장 수 | 관제사 · 상시 | 보고 요청 · 전화 확인 |
| 조치 완료율 | (종결 + 보고 미작성) ÷ 금일 접수 | 관제사 · 팀장 · 근무 교대 시 | 보고 미작성 건 종결 처리 |
| 초동 시간 | 접수 → 첫 현장 호출·외부 신고까지 평균 | 팀장 · 사후 검토 | 대응 지연 유형 점검 |
| 조치 시간 | 접수 → 조치 완료까지 평균 | 팀장 · 사후 검토 | 절차 개선 대상 식별 |
| 단계별 체류 시간 | 각 처리 단계에 머문 평균 시간 (진행 중 건 포함) | 팀장 · 사후 검토 | 병목 단계 확인 |
| 유형별 접수 | 분류 4종별 금일 접수 건수 | 팀장 · 일일 | 집중 관리 분류 확인 |
| 다발 사업장 | 사업장별 총 발생 횟수(반복 포함) 상위 3곳 | 팀장 · 일일 | 반복 원인 점검 요청 |

**검토 후 제외한 지표:** '전일 대비 접수 건수' — 일 평균 접수 건수가 적어 전일 대비 증감이 의미 있는 신호가 되기 어렵고, 관제사의 즉시 행동과 연결되지 않아 제외했습니다.

## 6. 외부 데이터 연계

| 데이터 | 출처 | 활용 |
|---|---|---|
| 초단기실황 · 초단기예보 | 기상청 단기예보 조회서비스 | 서해구·검단구 기온·강수·풍속, 6시간 예보 |
| 기상특보 | 기상청 기상특보 조회서비스 | 인천 지역 특보 발효 시 상단 표시 |
| 대기질 | 에어코리아 대기오염정보 | 측정소별 PM10·PM2.5 등급 |
| 도로 CCTV | 국가교통정보센터(ITS) 오픈API | 관할 경계 기준 주변 CCTV 실시간 영상 |
| 행정동 경계 | 행정동 경계 GeoJSON (2026.07판) | 서해구·검단구 지도 |
| 사업장 좌표 | OpenStreetMap Nominatim | 주소 → 좌표 변환, 실패 시 시설명 → 행정동 중심점 순으로 대체 |

- **영향 사업장 규칙:** 기상 조건(강수·폭염·미세먼지·강풍)이 발생하면 시설 성격(주차·공원·노인·청소년 등)에 맞는 사업장을 점검 대상으로 자동 표시
- **장애 대비:** API 일부가 실패하면 해당 항목만 대체값으로 표시하고 오류를 기록해 화면 전체가 멈추지 않도록 처리

## 7. 화면 구성

| 화면 | 이름 | 핵심 질문 |
|---|---|---|
| 1 | 긴급·미조치 알림 | 지금 무엇을 먼저 처리해야 하는가? (관제사 기본 화면 · 모든 처리 입력) |
| 2 | 지도 | 어디서 발생했고, 주변 날씨·대기 영향은? |
| 3 | 사업장별 현황 | 어느 사업장이 미조치·보고 지연·이상·연결 끊김인가? |
| 4 | 대응인력 현황 | 누가 대응해야 하고, 응답했는가? 부재자는? |
| 5 | CCTV 이벤트 연동 | 실제 상황인가, 오경보인가? |
| 6 | CCTV 상시 감시 | 평시 주요 구역 순환 감시 |

화면 1에서 상황을 선택하면 화면 2~5가 같은 상황·사업장으로 동기화됩니다.

## 8. 설계 원칙

- **탐지와 대응을 구분** — AI CCTV는 위험을 *탐지*하는 수단이고, 대시보드는 탐지 이후 *확인 → 판단 → 호출 → 조치 확인 → 기록*을 지원하는 업무 도구로 정의
- **1인 관제 = 정보 통합** — 한 사람이 모든 현장 대응을 하는 것이 아니라, 한 화면에서 우선순위를 판단하고 적절한 담당자를 호출·추적하는 구조
- **기록은 행동의 부산물** — 버튼을 누르는 순간 상황일지가 자동으로 쌓여, 별도 기록 업무 없이 처리 시간 지표가 산출되도록 설계
- **종결 조건 명시** — 조치 완료 단계 · 담당자 · 조치 메모 1건 · 보고서 필수 항목이 모두 채워져야 종결

## 9. 프로젝트 구조

```
├── main.py            서버 실행 · 라우팅 · 로그인
├── config.py          등급·처리 단계·호출 순서·사업장 등 설정값
├── state.py           상황 상태 모델 · 상태 변경 함수 · 지표 계산
├── loader.py          엑셀 읽기 + 행 단위 검증
├── weather.py         기상청 · 에어코리아 API
├── its.py             ITS CCTV API + 영상 중계
├── geo.py             행정동 경계 · 사업장 좌표 준비
├── screens/           화면 1~6, 공통 스타일, CCTV 재생
└── data/              지도 경계 데이터
```

### 실행 방법

```bash
pip install nicegui openpyxl httpx
python main.py        # http://localhost:8080
```

- 시연 데이터(`data/scenario.xlsx`, `data/facilities.xlsx`)와 사업장 사진·영상은 **기관 자료라 저장소에 포함하지 않았습니다.** 데이터 파일이 없으면 상황 목록이 빈 상태로 실행됩니다.
- `api_key.txt`(공공데이터포털), `its_key.txt`(국가교통정보센터) 인증키를 `main.py`와 같은 폴더에 두면 실시간 데이터를 사용합니다. 키가 없으면 대체값으로 동작합니다.

## 10. 한계와 다음 단계

| 한계 | 다음 단계 |
|---|---|
| 상황 데이터는 매뉴얼·담당자 인터뷰를 바탕으로 만든 **시연용 가상 시나리오** | 실제 상황일지 데이터로 유형별 발생 빈도 · 처리 시간 분포 기준선(baseline) 산출 |
